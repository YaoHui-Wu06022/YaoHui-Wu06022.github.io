AI Agent 系统设计

发表于2026-10-10
|总字数:3.3k|阅读时长:11分钟|浏览量:

Agent 基础

Agent 通常指能够感知环境、根据目标选择行动，并通过行动影响环境的系统

LLM-based Agent 则把大语言模型引入决策过程，使系统可以通过自然语言理解任务、选择工具、利用反馈调整后续行动。

Agent 与 LLM Application

普通 LLM 主要完成一次输入到输出的映射：

Agent 的区别是存在一个可重复的 Observe → Decide → Act 反馈循环

LLM 的一次回答可以是最终结果，也可以是中间行动

是否具有 Agent 特征，取决于模型是否能够在既定边界内动态决定执行过程

Workflow 与 Agent

Anthropic — Building effective agents

Anthropic 在这篇工程博客中使用了一个很有用的区分：

  • Workflow：LLM 和工具通过预先定义的代码路径进行编排
  • Agent：LLM 根据任务状态动态决定执行流程和工具使用方式
维度 Workflow Agent
执行路径 提前定义，允许少量条件分支 由模型与运行时状态共同决定
可预测性 较强 较弱
调试难度 相对较低 需要分析完整执行轨迹
成本与延迟 通常容易估计 与行动次数、工具结果有关
适合任务 步骤清晰、流程稳定 路径未知、需要动态探索

Agent 的发展脉络

从 Reasoning 到 Acting

[2210.03629] ReAct: Synergizing Reasoning and Acting in Language Models

在只生成推理文本的设定中，模型无法直接获取执行后的新证据，也不能自行调用环境中的能力

ReAct 的重要性在于提出了一个可以交替进行推理与行动的模式：

它使模型的下一步决策建立在新获得的环境反馈之上，而不是完全依赖最初 Prompt 中的信息

ReAct 的关键是行动与反馈的闭环

从 Tool Use 到 Tool Learning

[2302.04761] Toolformer: Language Models Can Teach Themselves to Use Tools

Toolformer 研究如何让语言模型学习：

  • 何时调用 API；
  • 选择哪个 API；
  • 如何构造 API 参数；
  • 如何将工具结果用于后续预测。

与在应用层通过 Prompt 或 Function Calling 选择工具不同，Toolformer 重点研究通过自监督数据构造和训练，使模型习得工具使用行为

从单次尝试到 Reflection

[2303.11366] Reflexion: Language Agents with Verbal Reinforcement Learning

Reflexion 的核心思想是：将任务失败、反馈和改进建议写成文本反思，保存在记忆中，供后续尝试使用

主要通过语言反馈和外部记忆改善下一次决策，而不是直接优化模型权重

从对话历史到可检索的记忆

[2304.03442] Generative Agents: Interactive Simulacra of Human Behavior

Generative Agents 使用 Memory Stream、Reflection、Planning 组织模拟角色的行为

长时间运行的 Agent 不必把全部历史原样塞入上下文，而可以从历史事件中提取记忆、形成抽象认识，再用于后续行动

论文设计了三个检索指标：

指标 含义 计算方式
Recency（时效性） 最近访问过的记忆更容易被检索 指数衰减，衰减系数 0.995
Relevance（相关性） 与当前情境越相关，分数越高 Embedding 余弦相似度
Importance（重要性） 重要事件应比普通事件优先 LLM 给出 1～10 分

从单 Agent 到 Multi-Agent

[2308.08155] AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

AutoGen 探索通过多个可对话的 Agent 组合模型、工具和人类参与者，由不同角色通过消息交互完成任务

将 Agent 统一抽象为能够发送、接收和响应消息的实体

Agent 的运行机制

Augmented LLM

Anthropic — Building effective agents

Agent 的基本构件可以理解为一个经过增强的 LLM：

  • Retrieval：获取模型参数以外的信息；
  • Tools：让模型发起外部查询、计算或修改；
  • Memory：保存和恢复跨步骤或跨会话的信息。

这三个能力不一定同时存在

关键不是 while，而是 环境反馈会改变下一步行动

例如：

Step 5 的选择无法仅凭任务最初的输入可靠确定，必须结合测试反馈

State 与 Context

State 是系统保存的真实执行状态，可以包含：

Context 是当前这一次 LLM 调用实际能看到的信息，是从 State、工具说明、外部检索、系统约束等来源组织出来的内容

State 不等于完整 Prompt；Context 也不等于长期记忆

终止条件

Agent 必须知道何时停止，常见条件包括：

  • Task Complete：目标已经达到，并获得必要的验证结果；
  • Max Iterations / Budget：超过预设步骤或资源上限；
  • Tool Failure：工具不可用或重试次数用尽；
  • Human Handoff：需要人工授权或进一步信息；
  • Unrecoverable Error：当前状态下无法安全继续。

如果只有“模型自己觉得完成了”，长期运行时可能出现提前结束、反复执行或无意义调用。

Decision 与 Planning

ReAct

[2210.03629] ReAct: Synergizing Reasoning and Acting in Language Models

ReAct 并不要求在任务开始时生成完整路线，而是在每次反馈后决定下一步

优势是灵活、容易利用新的证据；局限是局部决策可能反复探索，或者缺少全局任务约束。

Chain of Thought 与 Tree of Thoughts

[2201.11903] Chain-of-Thought Prompting Elicits Reasoning in Large Language Models

[2305.10601] Tree of Thoughts: Deliberate Problem Solving with Large Language Models

CoT 通过中间推理步骤组织问题求解，常见形式是一条推理路径

ToT 将问题求解视为对多个候选思路的搜索，可以评估、选择、回溯不同路径

方法 解决问题
CoT 如何组织单条多步推理路径
ToT 如何搜索、评估多个候选思路
ReAct 如何将决策与外部环境行动交替结合

Plan-and-Execute

与每一步只考虑下一动作不同，Plan-and-Execute 先将任务拆成一组子目标，再逐步执行。

固定计划的局限是：前面一步失败或发现新信息后，后续步骤可能已经不合适

因此实际系统经常加入 Replanning：

ReAct 强调逐步反馈，Plan-and-Execute 强调任务分解，两种思路可以组合

Function Calling

Function Calling 是 LLM 与软件执行环境之间的一种接口模式。

模型通常负责产生工具选择和结构化参数，真正的函数调用由外部运行完成

MCP

Architecture overview - Model Context Protocol

Specification - Model Context Protocol

MCP（Model Context Protocol） 是让 AI 应用以统一协议连接外部工具和上下文资源的开放协议

基本结构：

三个角色：

  • Host：用户交互的 AI 应用或 Agent 运行环境；
  • Client：运行在 Host 内，负责与某个 MCP Server 通信；
  • Server：对外提供可发现的能力或上下文。

MCP 与 Function Calling 不在同一抽象层：

  • Function Calling 关注模型如何提出工具调用；
  • MCP 关注外部能力如何被发现、描述并通过协议连接；
  • Agent 运行时负责决定何时调用，并处理结果和权限。

Agent Skills

Anthropic — Equipping agents for the real world with Agent Skills

Agent Skills 是将特定任务的程序性知识封装成可复用资源的一种方式

Anthropic 在 2025 年提出相关实践，并在之后将格式开放为跨平台标准

一个 Skill 一般包含：

SKILL.md 用于描述能力、使用条件、操作方式和注意事项，必要时再加载关联的脚本与资料

其关键设计是 Progressive Disclosure（渐进式披露）：

与每次把所有专业说明塞进 System Prompt 不同，Skills 能够按需加载上下文

概念 主要解决的问题
Tool Agent 可以执行什么操作
MCP 如何以通用接口连接工具与资源
Skill Agent 应当如何完成某类任务

Memory

LLM 的每次推理只能利用当次传入的上下文及模型参数中的知识

对于多步或跨会话任务，系统需要保留之前发生了什么

如果一直追加完整历史，上下文会持续增长，并混入越来越多与当前问题无关的信息

Memory 的核心不是单纯“保存更多”，而是在适当时机记录、检索、更新和遗忘信息。

Short-term Memory

保存当前对话、任务状态、最近的工具调用结果、临时推理信息等

  • 生命周期：通常随当前任务或会话结束而清理，也可以按需保留。
  • 常见载体：对话历史、上下文窗口、任务状态对象。

让 Agent 知道当前在做什么、已经做了什么、下一步应该做什么

Long-term Memory

保存未来可能再次使用的用户偏好、历史经验、项目背景、已验证的事实和工作流程

  • 生命周期：可以跨会话持久化，直到过期、被更新或删除
  • 常见载体：关系数据库、向量数据库、知识图谱、文件或持久化存储

让 Agent 在后续任务中复用历史信息，减少重复沟通和重复工作

Memory Retrieval

长期记忆需要选择性检索，可能使用：

  • Embedding Similarity；
  • Keyword Search；

长期记忆的难点不只有检索，还包括写入错误、信息过时、记忆冲突和隐私边界

Jev：面向决策的模型

Jev 是 TypeSafe AI 于 2026 年 9 月 15 日发布的决策模型

与 GPT、Qwen 等以自回归文本生成为主要输出方式的 LLM 不同，Jev 面向限定形式的判断任务，直接输出选项、评分及其对应的概率分布。

核心思想：对于可以拆解为明确判断的问题，不必让 LLM 生成一段文本再解析，而是直接获取结构化的决策结果和概率

核心能力

Jev 支持三类判断任务：

任务类型 含义 示例
Choice 从给定选项中选择一个 判断客服工单应该分配给哪个部门
Score 在有序等级中进行评分 判断客户的不满程度
Noul 判断一个陈述是否成立 判断一封邮件是否具有紧急性

模型直接返回结构化结果及相应概率，而不是生成完整的自然语言解释

核心技术特点

直接输出概率，减少文本生成开销

传统 LLM 通常需要经过逐 Token 解码才能生成 JSON 或文本，即使最终只需要一个分类结果，也可能产生不必要的生成开销

Jev不进行常规的逐 Token 文本生成，其多数查询的延迟约为 100 ms

支持通过自然语言定义任务

传统 BERT 分类器通常需要针对具体任务训练分类头，类别集合相对固定

Jev 允许调用方在请求中提供判断问题、选项和判定标准，从而支持多种判断任务，而不必为每个任务单独训练分类器

核心价值

将一部分 Agent 决策任务从通用文本生成转化为直接的概率判断

适合高频、低延迟、可拆解且具有明确判定标准的任务

在 Agent 工程中，可以采用“LLM 负责复杂推理与规划、Jev 负责快速判断、代码负责流程控制与确定性执行”的分工方式，减少不必要的文本生成开销，并为自动执行和人工接管提供概率参考
